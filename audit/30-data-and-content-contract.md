# 30 — Data and content contract

Status: INSPECTED from JSON/HTML/JS unless a validator is named. Machine-readable schema evidence lives in `audit/evidence/base-schema.json`, `audit/evidence/generated-data-schemas.json`, and `audit/evidence/content-field-lineage.json`.

## B1 exact schemas

The evidence JSON enumerates nested shapes and representative full records for `data/bases-index.json`, `data/rankings.json`, `data/discovery.json`, `data/interpretations.json`, `data/base-stats.json`, and `data/base-matrix-source.json`. Quiz questions/profiles are snapshotted in `audit/evidence/quiz-fixtures.json` because they are hard-coded JS constants, not source JSON.

Field categories and migration importance:

* system identity: `slug`, aliases, status and generated timestamps are system fields; editors should not freely mutate them without redirect/integrity checks.
* simple structured fields: name, country, region, type, coordinates and score numbers are suitable for constrained Supabase editing with validation and enum controls.
* relational structured data: rankings, similar bases, suggested comparisons, scenario ranks and related-base links should be derived/related records, not copied text.
* long-form plain/rich content: summaries, pillar narratives, strengths, weaknesses, best use, key risk, failure mode, survival-period copy and Field Manual chapters need editorial workflow beyond raw table cells.
* generated/derived values: rankings, percentiles, scenario entries, base stats, discovery/similarity, compatibility and sitemap should be regenerated.
* media metadata: image path, role, alt text, dimensions and social image mapping should become stable media records.

## B4 Supabase versus CMS evidence

INSPECTED conclusion: Supabase table editor is practical for constrained scalar fields and relationship maintenance only when guarded by validation. It is risky for rich narrative sections, arrays of callouts/FAQs, generated values, route slugs and media because accidental edits can break rendering, SEO, deterministic fixtures, or content hierarchy. CMS-style editing is better for Field Manual and long-form base narrative content; generated tables should be read-only to editors.

## B5 Field Manual extraction

INSPECTED in `field-manual.html` and `field-manual/index.html`: the Field Manual is static long-form HTML with hero metadata, reading-time UI, table of contents/anchor navigation, chapters/sections, paragraphs, lists, callouts, FAQs, further-reading panels and internal links. Reading time is calculated client-side from text length. Neutral migration representation: document metadata plus ordered blocks (`heading`, `paragraph`, `list`, `callout`, `faq`, `furtherReading`, `linkPanel`) with stable anchor IDs and link targets. This is representation guidance only, not a final CMS decision.

## B6 images and media

INSPECTED image locations: root legacy PNGs, `images/bases/*.png`, generated/copy thumbnails where present, `quiz.png`, placeholders and social/canonical references. Filename convention is slug-based PNG with fallback `/images/bases/placeholder.png`; explicit `base.image` overrides may exist. Current alt text is mostly base name/context generated by templates, not a separate media field. V2 migration requires mapping each GitHub path to a stable media record: `{sourcePath, canonicalSlug, role, altText, width, height, format, duplicateOf, consumers}`. Static map and secondary carousel future requirements are UNKNOWN in repository behaviour and require owner confirmation.
